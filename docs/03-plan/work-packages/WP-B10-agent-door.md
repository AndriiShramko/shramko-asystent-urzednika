# WP-B10 — The agent door (MCP and API for residents' AI assistants)

Kind: think (security) · Model tier: top; independent review · Depends on: WP-B7 items 1–3 (bundles, resolver, recommender), WP-B2 (visitor app), WP-B5 (checker), and for `fill_draft` at least one published descriptor from WP-B1 or WP-B6 · Branch: `wp/B10-agent-door`

Read first: `AGENTS.md`; [`docs/01-product/agent-door.md`](../../01-product/agent-door.md) (the idea, the two kinds of forms, the seven rules, the interface table, what is not claimed: that document is this package's specification); [`research/12`](../../../research/12-one-visit-package-addendum.md) items 14–16. Start only after the M2 gate. It is the optional third part of the demo; whatever does not reach its acceptance list is shown as "planned", never half-working. It splits naturally into two deliveries: **B10a** (items 1–7: public tools, slots, confirmation) and **B10b** (items 8–11: permission and draft filling).

Goal: a resident's own AI assistant can find the matter, get the complete set, hold a visit slot, and fill the digitised forms with its owner's data inside a permission the owner approved on their phone; the owner confirms, reads and submits.

Build, part a (no personal data anywhere):
1. **Service** `apps/agent-gateway`: a small Python service exposing the tools of the concept document twice: as an MCP server over HTTP built with the official Python SDK, and as plain HTTP routes under `/agent/v1/…` in the OpenAPI document. Both call the same functions; the functions call the resolver, catalogue, descriptors and checker of the other packages and nothing else. **Check the current protocol revision and SDK before coding** (transport and authorisation changed in 2026; research/12 item 15): pin the version and write it into the status file.
2. **Tool contracts** as typed models: closed enumerations for answers, ISO dates, opaque ids. Tool descriptions in English and Polish, one or two sentences each. Every list item in an output carries `source_url`, `source_date` and `catalogue_version`. Every form in a set carries `channel`: `online` or `counter` (from the bundle data; default `counter`). No free-text field in any output except titles and notes that come from the bundle data.
3. **Input guard for the public tools** (`find_matter`, `get_set`, `list_slots`, `hold_slot`, `get_visit`, `form_schema`, `request_permission`): any string argument matching identifier patterns (PESEL, document numbers, e-mail, phone) or longer than 300 characters is rejected with a clear error. Reuse the scan of WP-00. `find_matter` passes the sentence to the recommender with data class `PUBLIC`.
4. **Demo calendar:** `data/demo/slots.json` generated for the next ten working days (no real office calendar); in-memory holds with a time-to-live of ten minutes; at most two open holds per client address; a held slot is hidden from `list_slots`.
5. **Confirmation by the person:** `hold_slot` returns a confirmation address in the visitor app and the same as QR content. The page (`apps/visitor-pwa/src/features/confirm/`) shows matter, time and office and one button „Potwierdzam rezerwację". Only this turns the hold into `confirmed`. The page links to „Przygotuj wizytę" with the set pre-selected, so the `intent` of WP-B7 arrives at the counter with `source: "assistant"`.
6. **`get_visit`** returns the state, "co zabrać" and a calendar entry as iCalendar text (title, time, the office's address, the attachments in the description; no personal data).
7. **Clerk side:** a session whose intent has `source: "assistant"` shows „przygotowane przez asystenta mieszkańca" on the set panel. Nothing else differs.

Build, part b (personal data, only inside a permission):
8. **Permission:** `request_permission(matter_id, form_ids)` creates a pending request and returns an approval address and QR content. The approval page lists the matter, the forms and the lifetime (default 30 minutes) and offers „Pozwalam" and „Nie pozwalam". On approval the service issues an opaque permission token bound to the request, the forms and the right `fill_draft`; the assistant obtains it by polling `permission_status(request_id)`. One screen may carry both the booking confirmation and the permission. The token is never shown to the person and never logged in clear.
9. **`fill_draft(permission, form_id, person_role, values)`**: accepts only field paths that the form's descriptor marks as filled by the resident; anything else is an error naming the field. Values are validated by the descriptor's rules and by the checker (rules first; the model step only on a local provider or on pseudonymised text). The draft is kept in memory, encrypted with a key derived from a secret that only the person's approval page received (so the service cannot read a draft without the person's device; follow the handoff design of WP-B2), with a time-to-live equal to the permission's. Output: findings with severity and proposed fixes, share of fields filled, the address of „Mój wniosek". A second call replaces values; it never appends silently.
10. **„Mój wniosek"** (`apps/visitor-pwa/src/features/draft/`): the person opens the draft on their phone: the online form generated from the descriptor, filled, editable, with the findings. Actions: „Wyślij" for an `online` form (the prototype records a simulated filing and says so on the screen), „Zabierz na wizytę" for a `counter` form (the draft is moved into the phone's profile and deleted from the service), „Wycofaj" (deleted). `draft_status` reports the state without values.
11. **Audit, limits, lifecycle:** every call writes an event (tool, matter id, form id, permission id, result size, client address hash), never values or tokens; rate limit per address and per permission; drafts and permissions are destroyed on submit, on take-to-visit, on withdrawal and on expiry, each with an event; daily counters only.
12. **A page for people who want to connect an assistant**, „Dla asystentów AI": the address of the interface, what an assistant can and cannot do, in plain Polish; plus the machine-readable description at a stable address.
13. **Demo script** `tools/agent_door_demo.md`: the exact sentence, the expected tool calls, the synthetic notes the assistant fills from, and the fallback if the assistant on the laptop cannot reach the service (a recorded run).

Acceptance, part a:
- End-to-end test with an MCP client library: `find_matter` → `get_set` → `list_slots` → `hold_slot` → confirm in a headless phone-sized browser → `get_visit` returns `confirmed` and a valid iCalendar entry; the counter flow opens with the set marked as prepared by the assistant.
- A hold that is not confirmed expires and its slot is offered again.
- **Negative controls:** an argument of a public tool containing a synthetic PESEL is rejected and reaches neither a model nor a log; a third hold from the same address is refused; `get_set` with an unknown matter id returns an error, not a guess; the HTTP API and the MCP tools return identical results for the same input (property test over the demo bundles).
- The set returned by `get_set` equals the set of the clerk's screen for the same answers (same resolver; asserted in a test).

Acceptance, part b:
- End-to-end: `request_permission` → approval in the phone-sized browser → `fill_draft` with synthetic values containing one seeded mistake → the finding comes back → corrected call → „Mój wniosek" shows the values → „Zabierz na wizytę" → the draft is gone from the service and the counter handoff contains the values.
- **Negative controls:** `fill_draft` without a permission, with an expired one, with one issued for another form, and with a field the resident does not fill (for example the office section) are all refused; a refused permission never yields a token; after expiry the service holds no draft (inspect memory structures in the test); no value and no token appears in logs or audit events (scan with the synthetic identifiers); the service process alone cannot decrypt a stored draft (test with the person-side secret withheld).
- Nothing is submitted, signed or sent anywhere outside the prototype; the simulated filing is labelled on the screen and in `status.json`.
- The pages „Potwierdź", „Pozwól asystentowi", „Mój wniosek" and „Dla asystentów AI" pass the accessibility scan and work at 320 px.
- The status file records the protocol revision, the SDK version, the assistant used in the demo and what was simulated (calendar, filing, the identity behind the permission).

Not in scope: authorisation bound to a real identity (state login, wallet), any call to the city's booking system, electronic delivery or signature, any write to the person's calendar by our service (the assistant does that on the person's side), payment.

Ownership: `apps/agent-gateway/**`, `data/demo/slots.json`, `apps/visitor-pwa/src/features/confirm/**`, `apps/visitor-pwa/src/features/draft/**`, `tools/agent_door_demo.md` → WP-B10.
