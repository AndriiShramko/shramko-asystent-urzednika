# Цепочка проверки (WP-F11a), одна страница

## Что она проверяет
Цепочка прогоняет через сервис три набора файлов тем же путём, что и настоящий запрос (защита входа, затем конвейер), и для каждого файла ставит один из трёх исходов:

- **converted** (преобразован): получен JSON, он проходит строгую проверку `coi_lint` и шлюз.
- **refused** (отказ): сервис честно отказал и назвал причину по-польски. Это нормально, если отказ обоснован (например, формат RTF или картинка без OCR).
- **failed** (сбой): исключение, таймаут, падение процесса, отказ без польской причины или JSON не прошёл шлюз. Это всегда ошибка, ноль сбоев обязателен.

Наборы: **sets** (71 файл партнёра, лежат только локально), **unseen** (80 файлов из архива релиза `pre-event`, выбраны по зерну 20261121, в git только хеши), **hostile** (7 враждебных файлов, ждём отказ).

## Как читать «лучше / хуже»
Запуск: `bash tools/gate.sh py -m eval.chain --archive data/archive/files`. Сравнение с сохранённым эталоном `eval/chain/baseline.json` даёт для каждого файла:

- **хуже**: стало меньше полей, файл из converted стал refused или failed, число полей упало более чем на 20 процентов. Любое «хуже» печатается, и цепочка завершается с ненулевым кодом.
- **лучше**: полей стало больше или отказ превратился в результат. Это не ошибка; эталон обновляют осознанно.
- **без изменений**: ничего не печатается.

Сейчас сравнение с эталоном: 0 хуже, 0 лучше.

## Проверка самой цепочки
Принудительное исключение внутри конвейера даёт `failed` и ненулевой код выхода; эталон с одним лишним полем даёт «хуже». Оба случая закрыты тестами `eval/chain/tests/test_chain.py`.
